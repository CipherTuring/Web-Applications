## Objective

Build a REST API that stores and retrieves objects from a MySQL database **without writing SQL by hand**. Every `INSERT`, `SELECT`, `UPDATE`, and `DELETE` that reaches the database is generated by SQLAlchemy from ordinary Python object manipulation: creating an instance, assigning an attribute, appending to a list, or passing an object to `db.delete()`.

The domain is a small order-management system with four related entities: `Customer`, `Order`, `OrderItem`, and `Product`.

## Architecture

```
Python Client / curl
        │
        │ HTTP + JSON
        ▼
     FastAPI          ← validates input/output with Pydantic schemas
        │
        │ SQLAlchemy ORM
        ▼
      MySQL
```

Three layers, each with one job:

- **FastAPI** exposes the HTTP endpoints and validates the JSON that crosses the boundary (Pydantic schemas).
- **SQLAlchemy** maps Python classes to tables, tracks changes to loaded objects, and emits the SQL.
- **MySQL** stores the data and enforces the foreign keys.

The client is a completely separate program: it knows nothing about the ORM or the database, only about URLs and JSON.

## Data Model

```
Customer
   │
   └────< Order
             │
             └────< OrderItem >──── Product
```

| Entity | Purpose | Key relationships |
|---|---|---|
| `Customer` | Person who places orders | One-to-many with `Order`, **cascade** `all, delete-orphan` |
| `Order` | A purchase, with a date and a status | Belongs to one `Customer`; one-to-many with `OrderItem`, **cascade** `all, delete-orphan` |
| `OrderItem` | One line of an order: quantity and the price at purchase time | Belongs to one `Order` and points to one `Product` |
| `Product` | Item in the catalog, with price and stock | One-to-many with `OrderItem`, **no cascade** |

The cascade configuration is what makes deleting an `Order` remove its `OrderItem` rows while leaving the `Product` rows untouched: the order *owns* its items, but it only *references* products.

`unit_price` is stored on `OrderItem` on purpose — it is a snapshot of the product's price when the order was placed, so later price changes do not rewrite the history of past orders.

### How each module works

- **`database.py`** — Creates the `engine` (the connection pool to MySQL) and `SessionLocal`, the factory for sessions. `get_db()` is a FastAPI dependency that opens a session per request and closes it afterwards, so no session leaks between requests. `echo=True` prints every generated SQL statement to the console, which is how the ORM's behavior is observed.

- **`models.py`** — The four ORM classes. `mapped_column()` declares the columns, `ForeignKey` declares the database-level link, and `relationship()` declares the *object-level* link that lets Python navigate from an `Order` to its `Customer`. `back_populates` keeps both sides of a relationship in sync in memory: appending to `order.items` also sets `item.order`.

- **`schemas.py`** — Pydantic models that define what the API accepts and returns. They are **not** the ORM classes: an ORM class describes a table, a schema describes a JSON payload. The split is what lets the API expose a nested `Customer → Order → OrderItem → Product` structure while the tables stay flat and normalized. `from_attributes=True` lets a schema read directly from an ORM object.

- **`main.py`** — All endpoints. `Base.metadata.create_all()` runs at import time and creates any missing table from the model definitions, so the schema never has to be written as SQL.

- **`client.py`** — A standalone program that talks to the API over `requests`, with a text menu. It is the proof that the API is usable by anything that speaks HTTP, on this machine or another one.

## Key Mechanisms

### Nested insert

A single POST creates one `Order` plus all of its `OrderItem` rows:

```json
{ "customer_id": 1,
  "items": [ {"product_id": 1, "quantity": 2},
             {"product_id": 2, "quantity": 1} ] }
```

The endpoint never assigns a foreign key. It builds objects and links them:

```python
order = models.Order(customer=customer)      # sets orders.customer_id
item  = models.OrderItem(product=product)    # sets order_items.product_id
order.items.append(item)                     # sets order_items.order_id
db.add(order)                                # cascades to the items
db.commit()
```

At `commit()`, SQLAlchemy sorts the inserts by dependency: the order is inserted first, its generated `id` is read back, and only then are the items inserted with that value. Relationships, not manual IDs.

### Nested queries

`GET /orders/{id}` returns the order with its customer and, inside each item, the full product. Accessing `order.items` triggers a lazy `SELECT`, and `item.product` triggers another — the response schema simply walks the object graph, and the ORM fetches what it needs.

### Cascade delete

Deleting an `Order` emits a `DELETE` for its `order_items` rows before deleting the order itself, because of `cascade="all, delete-orphan"` on `Order.items`. The `Product` rows survive: `Product.order_items` has no cascade, so products are referenced, never owned.

### Transaction and inventory

`POST /orders` also decrements stock. Because the whole loop runs inside one transaction, the order, its items, and every stock change either all land or none do:

```python
try:
    for item_data in data.items:
        if product.stock < item_data.quantity:
            raise HTTPException(400, f"Insufficient stock for {product.name}")
        product.stock -= item_data.quantity
        order.items.append(item)
    db.add(order)
    db.commit()
except Exception:
    db.rollback()
    raise
```

If the third item fails, the stock already subtracted for the first two is undone by `db.rollback()` — nothing was written, because `commit()` was never reached. That is atomicity: the request is all-or-nothing.

### Final exercise

`GET /products/{id}/customers` walks the chain `Customer → Order → OrderItem → Product` backwards with two joins:

```python
select(models.Customer)
    .join(models.Customer.orders)
    .join(models.Order.items)
    .where(models.OrderItem.product_id == product_id)
    .distinct()
```

`.distinct()` matters because the join multiplies rows: a customer who bought the same product in three different orders would otherwise appear three times.

## Setup

**1. Create the database and user** (needs the MySQL root password):

```bash
mysql -u root -p < server/setup_database.sql
```

**2. Install the dependencies:**

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install fastapi uvicorn sqlalchemy pymysql pydantic email-validator requests
```

**3. Run the API** from the project root:

```bash
uvicorn server.main:app --host 0.0.0.0 --port 8000 --reload
```

The four tables are created automatically on startup. `--host 0.0.0.0` makes the API listen on every network interface, not just loopback, which is what allows a client on another computer to reach it.

**4. Run the client** in a second terminal:

```bash
python client/client.py
```

To use the client from a different computer, change `BASE_URL` in `client/client.py` to the server machine's LAN address (e.g. `http://192.168.1.50:8000`).
